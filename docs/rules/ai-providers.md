# Multi-AI-provider architecture — always follow

The AI model must be swappable at runtime. The app may use ChatGPT (OpenAI), Gemini, Grok, Claude, free/local models, or several paid accounts at once, and must switch automatically when one runs out of tokens/credits or fails. Adding a provider = new adapter module + config, nothing else.

- **One interface, many adapters.** Core code depends only on the `AiProvider` interface (`analyze(AnalysisRequest) → AiResponse`, `id()`, `capabilities()`, `healthCheck()`). Provider SDKs/DTOs stay inside their adapter package (e.g. `ai/openai`, `ai/gemini`, `ai/grok`, `ai/claude`, `ai/ollama`). Adapters are Spring beans keyed by provider type (e.g. `Map<AiProviderType, AiProviderFactory>`). Many providers expose OpenAI-compatible APIs (Grok, Ollama, OpenRouter, Groq) — reuse one generic OpenAI-compatible adapter with a different base URL where it works.
- **Providers are configuration.** `app.ai.providers[]`: `id` (alias, e.g. `claude-main`, `openai-work`, `gemini-free`, `ollama-local`), `type`, `model`, `baseUrl`, API key via env var, `priority`, `enabled`, `tier` (FREE/PAID), budgets (max tokens/requests/cost per day and per month), timeout. **The same provider type can appear multiple times** (e.g. two paid OpenAI accounts with different keys) — each entry is tracked independently.
- **Changing or retiring a provider.** An alias stands for one account at one provider, because its quota events, usage and budgets are tracked per alias. Provider rows are never deleted, since `ai_calls` and `signals` reference them.
  - Keep the alias for a new API key on the same account, or a new `model`. Every call and signal stores its own model, so results stay comparable across a model change. A model change clears `unavailable_until` and `unavailable_reason`, because they may only have applied to the old model; if the limit still applies, the next call stores it again.
  - Use a new alias for a different provider `type`, a different `baseUrl` or a different account (e.g. moving from a free to a paid account), and retire the old alias. A key must never follow its alias to another URL. Startup refuses a changed `type`; it can't detect a different account, so check this when editing `.env`.
  - To retire a provider, disable it at runtime, clear its key in `.env` or remove it from `app.ai.providers`. It's skipped from then on and its history stays. If no provider is left, runs produce HOLD (see below).
- **`AiRouter` with automatic failover.** Tries enabled providers in order of the configured strategy and skips any that are unavailable:
  - `PRIORITY` (default): fixed order by the `priority` number (1 = most preferred). **The actual order is TBD** — it must live only in config/DB (`priority` per provider, changeable at runtime), never hardcoded, so it can be decided and changed later without code changes.
  - `CHEAPEST_FIRST`: free tiers before paid, then by configured cost per token.
  - `ROUND_ROBIN`: spread load across equivalent accounts.
- **What triggers a fallback (technical failure only):** quota/credits exhausted or insufficient balance, rate limit (HTTP 429), auth error, server error (5xx), timeout, connection error, own budget limit reached, or a response that fails schema validation. Map each provider's native error codes to our `AiFailureReason` enum inside the adapter.
- **Token/quota exhausted → next model, with reset time stored in DB.** When a provider returns a "tokens used / quota exceeded / rate limit" error:
  1. The adapter extracts the **reset date and time** from the error (response body message, `Retry-After`, or `x-ratelimit-reset-*` style headers — each provider formats this differently; parse it inside the adapter) and converts it to an absolute UTC timestamp (`Instant`).
  2. The router immediately saves it to the database: `ai_providers.unavailable_until` = reset time, `unavailable_reason` = `QUOTA_EXHAUSTED` (or `RATE_LIMITED`), plus a row in `ai_quota_events` (provider id, model, reason, raw error message with secrets stripped, `detected_at`, `reset_at`, `reset_source` = `PROVIDER` or `ESTIMATED`).
  3. The **same analysis request** is retried right away on the next provider by priority (this counts as the one technical-failure fallback, not answer-shopping).
  - If the error contains no parseable reset time, estimate one from config (`defaultQuotaCooldown` per provider, e.g. 1 hour for rate limits, start of next day/billing period for daily/monthly quotas) and store it with `reset_source = ESTIMATED`.
  - Before every call the router reads `unavailable_until` from the DB and skips providers whose reset time is still in the future. Once `now >= unavailable_until`, the provider is eligible again and — because it has higher priority — **automatically takes over again** (optionally after a cheap `healthCheck()`). If it fails again, store the new reset time.
  - The DB is the source of truth so this survives restarts and is visible in the UI (`GET /api/ai/providers` shows `unavailableUntil` per provider). All timestamps in UTC.
- **Other failures (cooldown / circuit breaker).** Server errors, timeouts and connection errors mark the provider unavailable for a short configurable cooldown with backoff; auth errors keep it unavailable until config changes. Same DB fields (`unavailable_until`, `unavailable_reason`).
- **Track usage ourselves.** Record tokens/requests/estimated cost per provider per call in `ai_calls`, and stop using a provider *before* it hits its configured budget — don't rely only on the provider returning an error.
- **All providers down → HOLD.** If no provider returns a valid response, the run produces no signal/order (stored as HOLD with reason `NO_AI_PROVIDER_AVAILABLE`) and the event is logged. Never trade without a validated AI response.
- **Safety: no answer-shopping.** Fallback is only for *technical* failures. Never call another provider because a valid answer was HOLD, low-confidence, or rejected by risk checks. One analysis run = one accepted response.
- **Same prompt, same schema.** All providers get the same prompt template and must return the same JSON signal schema, validated by the same strict parser. Provider-specific tweaks (JSON mode, structured outputs, system prompt format) live in the adapter. Don't let a provider's free-form text through.
- **Model-agnostic results.** Each stored signal records `aiProvider` (alias), `aiModel`, and `fallbackFrom` (the providers skipped and why) so results can be compared across models.
- **Runtime control.** Providers can be enabled/disabled and reordered at runtime via the settings API (stored in DB, overriding config defaults), without restart. API keys are never sent to or editable from the frontend.
- **Tests.** A shared `AiProvider` contract test suite plus a `FakeAiProvider` that can simulate success, malformed output, 429, quota exhaustion and timeouts. Router tests must cover fallback order, quota error → reset time saved to DB → next provider used → original provider used again after reset time, missing reset time → estimated, reset-time parsing per adapter (with real recorded error samples), cooldown, budget limits, all-down → HOLD, and no fallback on valid HOLD answers. Never call real paid APIs in tests.
