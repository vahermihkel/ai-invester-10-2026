# Multi-broker architecture — always follow

Code must work for IBKR, eToro **and any broker added later** without changing core logic. Adding a new broker = adding a new adapter module + config, nothing else.

- **One interface, many adapters.** Core code (scheduler, AI engine, risk engine, execution service, controllers) depends only on the `BrokerClient` interface and broker-neutral domain types. Never import IBKR (`com.ib.*`) or eToro classes/DTOs outside their own adapter package (e.g. `broker/ibkr`, `broker/etoro`).
- **`BrokerClient` covers at least:** `connect`/`disconnect`/`isConnected`, `getAccountSummary`, `getPositions`, `getOpenOrders`, `placeOrder(OrderRequest)`, `cancelOrder`, `getOrderStatus`, `getFills`, `resolveInstrument(symbol)`, `isMarketOpen(instrument)`, `capabilities()`. All async methods return `CompletableFuture`; all results are our own domain records.
- **Broker-neutral domain model.** `Instrument`, `OrderRequest`, `Order`, `Fill`, `Position`, `AccountSummary`, `OrderStatus` are our own records. Each adapter maps to/from the broker's native format (IBKR `Contract`/`Order`, eToro instrument IDs / amount-based positions, etc.) and maps broker statuses and errors to our enums/exceptions.
- **Capabilities, not `if (broker == X)`.** Each adapter declares a `BrokerCapabilities` record (e.g. supported order types, fractional quantities, size by amount vs. by units, short selling, leverage/CFD, supported asset classes, min order size, rate limits, position model: netting vs. separate positions). Core code checks capabilities and rejects (stores the rejection reason) instead of branching on broker name. Example: eToro opens positions by cash amount, IBKR by share quantity — the execution service converts via capabilities and current price, using `BigDecimal`.
- **Position model.** On a netting broker a SELL reduces the one position. On a broker with separate positions a SELL may open a short instead of closing a long, so a close must name the position: `OrderRequest` carries `positionEffect` (OPEN/CLOSE) and `brokerPositionId`, and the execution service fills them in based on the capability. See [database.md](../skills/database.md).
- **Instrument mapping.** Our canonical key is the symbol (+ exchange/currency where needed). Each adapter resolves it to the broker's own ID (IBKR `conId`, eToro `instrumentId`, …) and caches it in `instrument_mappings`, with its trading rules (multiplier, min quantity, quantity step, price tick) and anything broker-specific in `details`. Every order, trade and position snapshot references the resolved row. If a symbol can't be resolved unambiguously → no order.
- **Activity we didn't start.** The broker can change the account without us: the user trades in the broker's own app, a stop-loss triggers, a position is liquidated, a dividend or deposit arrives. Adapters report these and we store them: orders as `source = EXTERNAL` (no `client_order_id`; if the broker has no order for the event, the adapter derives a stable `broker_order_id`), money movements in `cash_transactions`.
- **Accounts are configuration.** Brokers/accounts are defined in config (`app.brokers.accounts[]`: alias, broker type, environment PAPER/LIVE); credentials come from `.env`, and an account is enabled only when its `.env` values are filled in ([configuration.md](configuration.md)). An existing alias can't change broker or environment: startup refuses it, because its history would then be attributed to the wrong account. Every signal and order is stored with its account alias; never a "default broker" hidden in code. Adapters are discovered as Spring beans keyed by broker type (e.g. `Map<BrokerType, BrokerClientFactory>`).
- **Changing or retiring an account.** An alias stands for one real broker account, because its history hangs off it. Account rows and their history are never deleted.
  - Keep the alias for new API keys or a new host/port on the same account, or a new display name.
  - Use a new alias for a different broker, a different PAPER/LIVE environment, or a different account at the same broker (e.g. another `IBKR_PAPER_ACCOUNT_ID`), and retire the old alias. Startup refuses the first two; it can't detect the third, so check this when editing `.env`.
  - To retire an account, in this order: (1) switch away from it; (2) cancel its open orders or wait until they finish, and close its positions at the broker if they shouldn't stay open, because the app doesn't close them and stops watching them once the account is disabled; (3) clear its `.env` values or remove it from `application.yml`. A retired account is disabled and can't be made active.
  - The order matters because a disabled account has no connection, so it can't be reconciled. If an account is disabled while it still has open orders in our DB, startup warns and writes an audit entry naming the account. Those orders keep their last known status (never assumed filled or cancelled) until the account is enabled again or a backfill resolves them.
  - An adapter's code can be removed once no account using it has open orders. History is served from our DB, so it doesn't need the adapter.
- **One active account at a time.** The user trades with one broker at a time. Exactly one configured account is *active* (or none): only it is analysed for, traded and shown in the UI.
  - Default from `ACTIVE_ACCOUNT` in `.env`; runtime changes via `PUT /api/accounts/active`, persisted in the DB (survives restarts). If `ACTIVE_ACCOUNT` in `.env` changed since the last start, the `.env` value wins ([configuration.md](configuration.md)).
  - Switching must be effortless: one dropdown + confirmation in the UI header, no restart, no code or config change. Core code always asks an `ActiveAccountService` for the active account; never cache it outside that service.
  - Switching is atomic and logged (from, to, timestamp UTC). A running analysis run finishes on the account it started with; the next run uses the new account.
  - Switching does **not** cancel orders or close positions on the previous account; they stay at the broker. The backend keeps reconciling that account's open orders/fills until none are left, so history stays complete.
  - Switching to a disabled/unknown account is refused. Switching to a LIVE account is refused unless `ALLOW_LIVE_TRADING=true` in `.env` (default `false`); the UI shows an extra warning.
  - Only the active account's broker connection must be kept up; other adapters may disconnect once they have no open orders left to reconcile.
- **Per-account data.** Risk limits, daily loss/trade counters, reconnect state and idempotency checks are tracked per account, so each broker keeps its own limits and history when you switch back and forth.
- **History: own DB is the record, broker is the source of truth.** Live state (balance, positions, open orders) is read from the broker. History (orders, fills, signals, equity over time) is served from our DB, because broker APIs only return short windows (IBKR `reqExecutions`/`reqCompletedOrders` ≈ current day up to ~7 days; no balance history via the TWS API) and don't know our signals/AI reasoning/risk decisions. So:
  - Orders are stored before sending and updated from broker callbacks; fills are stored as they arrive.
  - Equity/positions are snapshotted periodically (`account_snapshots` + `position_snapshots`, with `reason` = SCHEDULED / AFTER_FILL / ANALYSIS_RUN / END_OF_DAY, see [database.md](../skills/database.md)), which is how balance history exists. Snapshot schedule (intervals configurable, e.g. `app.snapshots.*`, not hardcoded):
    - every 15 min while the account's market is open;
    - after every fill;
    - at the start of each analysis run (the same data goes into the AI prompt);
    - once after market close — the end-of-day record, reconciled against the broker's daily history (e.g. IBKR Flex daily NAV);
    - hourly while the market is closed, only if the account holds 24/7 instruments (e.g. crypto).
  - Retention: keep intraday snapshots ~90 days, then delete all but the `END_OF_DAY` snapshot per day (at most one per account per UTC day).
  - Snapshots are for history/charts only. Risk checks (e.g. max daily loss) use live values from the broker right before each order, never a snapshot.
  - A reconciliation/backfill job per adapter compares our DB with the broker's history source and fills gaps (e.g. app was offline; backfilled snapshots, fills and cash transactions get `source = BACKFILL`, and snapshots keep only the values the history source really has): IBKR via the **Flex Web Service** (Flex Queries: trades, cash, daily NAV, up to 365 days per query, end-of-day data); eToro via its trade-history endpoint (verify in current eToro API docs). This is an optional `BrokerClient` capability; brokers without a history source rely on our DB only.
- **Same safety rules for every broker.** Every adapter must implement paper/live separation, reconnect + resync, idempotent ordering and full logging (see [safety.md](safety.md)). A new adapter isn't done until it has these.
- **Contract tests.** One shared abstract test suite for the `BrokerClient` contract that every adapter (and the in-memory `FakeBrokerClient` used in tests) must pass. Adapter-specific mapping tests use recorded/mocked broker responses, never a real account.
